## 1. 目的

PlantUML で管理しているソフトウェア設計図を、**書きやすく・見やすく・素早く**編集できるデスクトップエディターを作る。
GitHub で公開し、社内でもそのまま導入できる品質（ドキュメント・テスト・配布物）を保つ。

### 1.1 解決したい課題（現状の不満）

- 汎用エディター + プラグインでは、プレビューの追従・エラー位置の把握・図の書き出しが煩雑
- 社内の設計図を外部の PlantUML サーバーへ送りたくない（機密性）
- 導入手順が人によってバラバラ

### 1.2 スコープ外（当面やらないこと）

- PlantUML 以外の記法（Mermaid 等）のサポート
- 図形をマウスで描く GUI エディター（将来候補として検討のみ）
- クラウド同期・共同編集
- **macOS 対応**（ADR-0005。動作確認・配布・不具合対応をしない）

## 2. 技術スタック

社内試作と同じ構成を踏襲する。選定理由は ADR に記録する（`docs/adr/`）。

| 層               | 採用技術                                                                       | 備考                                         |
| ---------------- | ------------------------------------------------------------------------------ | -------------------------------------------- |
| デスクトップ基盤 | **Tauri 2**                                                                    | 軽量。対象は Windows / Linux（ADR-0005）     |
| バックエンド     | **Rust**（stable）                                                             | ファイル I/O、レンダリング呼び出し、設定管理 |
| フロントエンド   | **TypeScript + React + Vite**                                                  | 試作の構成に合わせて変更可（ADR-0002）       |
| エディター部品   | **CodeMirror 6**                                                               | 軽量・拡張しやすい。Monaco は代替案          |
| スタイル         | CSS Modules または Tailwind CSS                                                | モダンなデザイン・ダーク/ライト対応          |
| レンダリング     | **ローカル plantuml.jar（Java）** を既定、**社内 PlantUML サーバー**を任意設定 | 外部送信しないことを既定にする（ADR-0003）   |
| テスト           | cargo test / Vitest / Playwright（または WebdriverIO + tauri-driver）          | 詳細は `test-strategy.md`                    |
| CI/CD            | GitHub Actions（Windows / Linux）                                              | lint・テスト・ビルド・リリース               |

## 3. 開発の進め方

### 3.1 フェーズ構成（2026-11-15 改訂）

開発を 3 つのフェーズに分ける。**土台ができたら、実際に動かしながらユースケース単位で作り込む**。

| フェーズ                      | イテレーション            | 進め方                                                                                           | テストの厳密さ                                           |
| ----------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| A. 土台づくり                 | 0〜1                      | 計画駆動。受け入れ基準を先に決めて実装する                                                       | **厳密**（単体・結合・E2E）                              |
| B. ユースケース駆動の作り込み | 2〜（要件が出そろうまで） | 利用者が実際に動かし、使いたい機能を特定 → 実装 → 正常系を動かして確認、を短いサイクルで繰り返す | **軽量**（正常系の確認が中心。単体テストは必須にしない） |
| C. 固めと配布                 | 最終                      | 要件が出そろってから、テストを補強し、インストーラーを作って v1.0 を出す                         | **厳密**（フェーズ B で省いたテストを補う）              |

**フェーズ B を軽量にする理由**：使いながら要件を出し切ることが目的で、細かい設計変更が頻繁に起きる。この段階で単体テストを厳密に書くと、変更のたびに書き直しになり、要件探索の速度が落ちる。

### 3.2 完了の定義（Definition of Done）

**全フェーズ共通**

1. CI（lint / 型チェック / 既存テスト / ビルド）が Windows・Linux で成功している（既存のテストは壊さない。仕様変更で不要になったテストは削除してよい）
2. `cargo fmt` / `cargo clippy -D warnings` / ESLint / Prettier の指摘ゼロ
3. ユーザー向けの変更は `CHANGELOG.md` に反映済み
4. 機密情報（社内の図、パス、URL 等）がリポジトリに含まれていない

**フェーズ A・C で追加**

5. 受け入れ基準をすべて満たし、確認結果を `docs/iterations/itN.md` に記録している
6. 単体テスト・E2E テストが追加されている（`docs/test-strategy.md` の目標値）
7. `docs/user-guide.md`・ADR を更新済み

**フェーズ B で追加**

5. 対象ユースケース（`docs/requirements.md` の UC-xx）の**正常系を実際に操作して確認**し、結果を `docs/iterations/itN.md` に記録している
6. 確認中に見つかった新しい要望・不満は、捨てずに `docs/requirements.md` のバックログへ書き足している
7. 設計判断が大きく変わったときだけ ADR を書く（細かい変更は CHANGELOG とイテレーション記録で足りる）

### 3.3 ドキュメント体系

| ファイル                   | 内容                                                  | 更新タイミング       |

### イテレーション 1：MVP「書いて見られる」（フェーズ A）

**目的**：最小限だが日常的に使える状態。**ここから利用者が実際に動かし、フェーズ B のユースケース洗い出しを始める。**

| 成果物           | 内容                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| エディター画面   | 左：テキストエディター、右：プレビューの 2 ペイン（境界ドラッグで幅変更）  |
| ファイル操作     | 新規 / 開く / 保存 / 名前を付けて保存（`.puml` `.plantuml` `.pu` `.iuml`） |
| ライブプレビュー | 入力停止後 300ms で SVG を再描画                                           |
| エラー表示       | PlantUML の構文エラーを行番号付きで表示                                    |
| レンダラー層     | Rust 側に `Renderer` トレイト、実装 1：ローカル plantuml.jar               |
| 設定             | Java パス・plantuml.jar パスの指定（未設定時は自動検出）                   |

**受け入れ基準**

- [ ] AC1-1：`.puml` ファイルを開くと 3 秒以内にプレビューが表示される（100 行程度のクラス図）
- [ ] AC1-2：テキストを編集すると、入力停止後 1 秒以内にプレビューが更新される
- [ ] AC1-3：構文エラーがある場合、エラー行番号とメッセージが表示され、直前の正常なプレビューは残る
- [ ] AC1-4：保存したファイルが他のエディター（VS Code 等）でそのまま開け、文字コードは UTF-8・改行コードは元ファイルを維持する
- [ ] AC1-5：未保存の変更がある状態で閉じようとすると確認ダイアログが出る
- [ ] AC1-6：Java が見つからない場合、原因と対処方法が画面に表示される（クラッシュしない）
- [ ] AC1-7：レンダリング処理・ファイル I/O に単体テスト、主要操作（開く→編集→保存）に E2E テストがある

### イテレーション 2 以降：ユースケース駆動の作り込み（フェーズ B）

**目的**：利用者が実際に動かしながら、使いたい機能と要件を出し切る。

**1 サイクルの流れ**（数日〜1 週間程度。固定の期間は設けない）

1. **動かす**：利用者が最新版で実際の作業（設計図の作成・修正）をしてみる
2. **特定する**：「こうしたい」「ここが不便」をユースケースとして `docs/requirements.md` に書く（UC-xx：誰が・何をしたいか・正常系の流れ）
3. **選ぶ**：次のサイクルで扱うユースケースを利用者が決める（`docs/iterations/itN.md` に記載）
4. **作る**：正常系が動くところまで実装する。異常系・細部は、困ったら次のサイクルで扱う
5. **確かめる**：利用者と一緒に正常系を操作して確認する。新しく出た要望はバックログへ

**受け入れ基準の書き方**：ユースケースごとに「この操作をしたら、こうなる」を 1〜3 行で書き、利用者が操作して確認できたら合格とする。性能などの数値基準は、利用者が不満を感じたときに追加する。

**テスト**：既存の自動テストは CI で維持する。新しい機能には、壊れると困る中核のロジックに限って簡単なテストを足す（任意）。詳細は `docs/test-strategy.md` 4章。

#### 作り込みの候補（当初計画から移したもの。採否・順番は動かしながら決める）

| 分類           | 候補                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| エディター     | シンタックスハイライト、補完、エラー行マーカーとジャンプ、マルチタブ、最近使ったファイル、テーマ切り替え   |
| プレビュー     | ズーム・パン・全体表示、1 ファイル内の複数図の切り替え、プレビューからソース行へジャンプ                   |
| 書き出し       | SVG / PNG 書き出し、クリップボードへコピー                                                                 |
| ワークスペース | フォルダを開く（ファイルツリー）、`!include` 対応、外部変更の検知、全文検索                                |
| 性能           | JVM 常駐による描画の高速化（ADR-0003）                                                                     |
| その他         | テンプレート / スニペット、アウトライン表示、Git 差分の図での比較、フォーマッター、簡易 GUI 編集、多言語化 |

### 最終イテレーション：固めと配布（フェーズ C）

**開始の目安**：利用者が「主な使い方は一通りできる」と判断し、`docs/requirements.md` の必須ユースケースがすべて動いたとき。

| 成果物           | 内容                                                                            |
| ---------------- | ------------------------------------------------------------------------------- |
| テストの補強     | フェーズ B で実装した機能の単体テスト・E2E テストを、確定した仕様に合わせて追加 |
| インストーラー   | Windows（MSI / NSIS）、Linux（AppImage / deb）                                  |
| リリース自動化   | タグ push で GitHub Releases にビルド成果物を添付                               |
| レンダラー追加   | 社内 PlantUML サーバー（URL 指定）を選択可能に（必要な場合）                    |
| 自動更新（任意） | Tauri updater による更新通知                                                    |
| 社内導入ガイド   | プロキシ環境・Java 未導入 PC 向けの手順                                         |
| 文書の整備       | ユーザーガイド・アーキテクチャ・ADR を最終仕様に合わせて更新                    |

**受け入れ基準**

- [ ] ACC-1：必須ユースケースすべてに自動テスト（単体または E2E）があり、`docs/test-strategy.md` 3章の目標値を満たす
- [ ] ACC-2：`v*` タグを push すると、Windows・Linux のインストーラーが GitHub Releases に自動で添付される
- [ ] ACC-3：管理者権限のない社内 PC で、導入ガイドどおりにインストールして使える
- [ ] ACC-4：サーバーレンダラーを入れた場合、指定 URL 以外へ通信しないことをテストで確認済み
- [ ] ACC-5：`v1.0.0` として README・ユーザーガイド・CHANGELOG が最新である

## 5. 未決事項（イテレーション 0 で決める）

| #   | 論点                         | 推奨案                                                               | 理由                                                                     |
| --- | ---------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| D1  | レンダリング方式             | ローカル plantuml.jar を既定、サーバーは任意設定                     | 社内の図を外部送信しない。サーバー方式は Java 不要だが情報管理上のリスク |
| D2  | Java の扱い                  | 利用者が Java を導入（同梱しない）。将来 jlink で最小 JRE 同梱を検討 | 初期は配布物を軽く保つ                                                   |
| D3  | アプリのライセンス           | MIT または Apache-2.0                                                | 社内利用・改変がしやすい                                                 |
| D4  | plantuml.jar の同梱          | MIT 版 plantuml（plantuml-mit）を同梱、または初回起動時に案内        | GPL 版の同梱は配布条件に注意                                             |
| D5  | フロントエンド FW            | React（試作が別 FW ならそれに合わせる）                              | 試作資産の流用                                                           |
| D6  | 公開リポジトリ名・アカウント | 個人アカウントで公開し、社内からは Releases を利用                   | 会社の公開ポリシーを確認                                                 |

## 6. リスクと対策

| リスク                              | 影響            | 対策                                                                                     |
| ----------------------------------- | --------------- | ---------------------------------------------------------------------------------------- |
| Java 未導入 PC が多い               | MVP が使えない  | 分かりやすいエラー表示＋導入ガイド、将来 JRE 同梱やサーバー方式                          |
| 大きな図でレンダリングが遅い        | 編集体験の悪化  | デバウンス、レンダリングの直列化・古い要求のキャンセル、常駐 JVM（`-pipe` モード）の検討 |
| E2E テストが不安定                  | CI の信頼性低下 | E2E は主要シナリオに絞り、ロジックは単体テストで担保                                     |
| 社内ポリシーで OSS 公開が制限される | 公開できない    | D6 を早期に確認、社内情報を含めない運用（DoD 6）                                         |
