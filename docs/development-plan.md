## 1. 目的

PlantUML で管理しているソフトウェア設計図を、**書きやすく・見やすく・素早く**編集できるデスクトップエディターを作る。
GitHub で公開し、社内でもそのまま導入できる品質（ドキュメント・テスト・配布物）を保つ。

### 1.1 解決したい課題（現状の不満）

- 汎用エディター + プラグインでは、プレビューの追従・エラー位置の把握・図の書き出しが煩雑
- 社内の設計図を外部の PlantUML サーバーへ送りたくない（機密性）
- 導入手順が人によってバラバラ

### 1.2 スコープ外（当面やらないこと）

- PlantUML 以外の記法（Mermaid 等）のサポート
- 図形をマウスで描く GUI エディター（将来候補として検討のみ）
- クラウド同期・共同編集

## 2. 技術スタック

社内試作と同じ構成を踏襲する。選定理由は ADR に記録する（`docs/adr/`）。

| 層               | 採用技術                                                                       | 備考                                         |
| ---------------- | ------------------------------------------------------------------------------ | -------------------------------------------- |
| デスクトップ基盤 | **Tauri 2**                                                                    | 軽量・クロスプラットフォーム                 |
| バックエンド     | **Rust**（stable）                                                             | ファイル I/O、レンダリング呼び出し、設定管理 |
| フロントエンド   | **TypeScript + React + Vite**                                                  | 試作の構成に合わせて変更可（ADR-0002）       |
| エディター部品   | **CodeMirror 6**                                                               | 軽量・拡張しやすい。Monaco は代替案          |
| スタイル         | CSS Modules または Tailwind CSS                                                | モダンなデザイン・ダーク/ライト対応          |
| レンダリング     | **ローカル plantuml.jar（Java）** を既定、**社内 PlantUML サーバー**を任意設定 | 外部送信しないことを既定にする（ADR-0003）   |
| テスト           | cargo test / Vitest / Playwright（または WebdriverIO + tauri-driver）          | 詳細は `test-strategy.md`                    |
| CI/CD            | GitHub Actions（Windows / macOS / Linux）                                      | lint・テスト・ビルド・リリース               |

## 3. 開発の進め方

### 3.1 イテレーション方式

- 1 イテレーション = **1〜2 週間程度**を目安に、**毎回「動くもの」をリリース**する（`v0.x.0` タグ）
- 各イテレーションは「計画 → 実装 → テスト → ドキュメント更新 → 受け入れ確認 → 振り返り」の順で進める
- 受け入れ基準を満たさない機能は次イテレーションへ持ち越す（中途半端にマージしない）

### 3.2 全イテレーション共通の完了の定義（Definition of Done）

すべての機能・PR は以下を満たしたときに「完了」とする。

1. 受け入れ基準をすべて満たし、確認結果を `docs/iterations/itN.md` に記録している
2. 自動テストが追加されており、CI（lint / 型チェック / テスト / ビルド）が 3 OS で成功している
3. `cargo fmt` / `cargo clippy -D warnings` / ESLint / Prettier の指摘ゼロ
4. ユーザー向けの変更は `CHANGELOG.md` と `docs/user-guide.md` に反映済み
5. 設計判断を伴う変更は ADR を追加・更新済み
6. 機密情報（社内の図、パス、URL 等）がリポジトリに含まれていない

### 3.3 ドキュメント体系

| ファイル                   | 内容                                                  | 更新タイミング       |
| -------------------------- | ----------------------------------------------------- | -------------------- |
| `README.md`                | 概要・インストール・クイックスタート                  | リリースごと         |
| `docs/development-plan.md` | 本書。全体計画                                        | イテレーション計画時 |
| `docs/requirements.md`     | 機能要件・非機能要件の一覧（ID 付き）                 | 要件追加時           |
| `docs/architecture.md`     | 構成図（PlantUML で記述！）、モジュール責務、IPC 一覧 | 構造変更時           |
| `docs/test-strategy.md`    | テスト方針・テストレベル・カバレッジ目標              | 方針変更時           |
| `docs/adr/NNNN-*.md`       | 設計判断の記録                                        | 判断のたび           |
| `docs/iterations/itN.md`   | 各イテレーションの計画・受け入れ結果・振り返り        | イテレーションごと   |
| `docs/user-guide.md`       | 利用者向け操作説明                                    | 機能追加時           |
| `CONTRIBUTING.md`          | 開発環境構築・ブランチ運用・PR ルール                 | 運用変更時           |
| `CHANGELOG.md`             | Keep a Changelog 形式の変更履歴                       | PR ごと              |

> 設計図は自作エディターで書く（ドッグフーディング）。`docs/architecture.md` の図は `docs/diagrams/*.puml` として管理する。

### イテレーション 1：MVP「書いて見られる」

**目的**：最小限だが日常的に使える状態。**ここで初めて社内で試用してもらう。**

| 成果物           | 内容                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| エディター画面   | 左：テキストエディター、右：プレビューの 2 ペイン（境界ドラッグで幅変更）  |
| ファイル操作     | 新規 / 開く / 保存 / 名前を付けて保存（`.puml` `.plantuml` `.pu` `.iuml`） |
| ライブプレビュー | 入力停止後 500ms で SVG を再描画                                           |
| エラー表示       | PlantUML の構文エラーを行番号付きで表示                                    |
| レンダラー層     | Rust 側に `Renderer` トレイト、実装 1：ローカル plantuml.jar               |
| 設定             | Java パス・plantuml.jar パスの指定（未設定時は自動検出）                   |

**受け入れ基準**

- [ ] AC1-1：`.puml` ファイルを開くと 3 秒以内にプレビューが表示される（100 行程度のクラス図）
- [ ] AC1-2：テキストを編集すると、入力停止後 1 秒以内にプレビューが更新される
- [ ] AC1-3：構文エラーがある場合、エラー行番号とメッセージが表示され、直前の正常なプレビューは残る
- [ ] AC1-4：保存したファイルが他のエディター（VS Code 等）でそのまま開け、文字コードは UTF-8・改行コードは元ファイルを維持する
- [ ] AC1-5：未保存の変更がある状態で閉じようとすると確認ダイアログが出る
- [ ] AC1-6：Java が見つからない場合、原因と対処方法が画面に表示される（クラッシュしない）
- [ ] AC1-7：レンダリング処理・ファイル I/O に単体テスト、主要操作（開く→編集→保存）に E2E テストがある

## 5. 未決事項（イテレーション 0 で決める）

| #   | 論点                         | 推奨案                                                               | 理由                                                                     |
| --- | ---------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| D1  | レンダリング方式             | ローカル plantuml.jar を既定、サーバーは任意設定                     | 社内の図を外部送信しない。サーバー方式は Java 不要だが情報管理上のリスク |
| D2  | Java の扱い                  | 利用者が Java を導入（同梱しない）。将来 jlink で最小 JRE 同梱を検討 | 初期は配布物を軽く保つ                                                   |
| D3  | アプリのライセンス           | MIT または Apache-2.0                                                | 社内利用・改変がしやすい                                                 |
| D4  | plantuml.jar の同梱          | MIT 版 plantuml（plantuml-mit）を同梱、または初回起動時に案内        | GPL 版の同梱は配布条件に注意                                             |
| D5  | フロントエンド FW            | React（試作が別 FW ならそれに合わせる）                              | 試作資産の流用                                                           |
| D6  | 公開リポジトリ名・アカウント | 個人アカウントで公開し、社内からは Releases を利用                   | 会社の公開ポリシーを確認                                                 |

## 6. リスクと対策

| リスク                              | 影響            | 対策                                                                                     |
| ----------------------------------- | --------------- | ---------------------------------------------------------------------------------------- |
| Java 未導入 PC が多い               | MVP が使えない  | 分かりやすいエラー表示＋導入ガイド、将来 JRE 同梱やサーバー方式                          |
| 大きな図でレンダリングが遅い        | 編集体験の悪化  | デバウンス、レンダリングの直列化・古い要求のキャンセル、常駐 JVM（`-pipe` モード）の検討 |
| E2E テストが不安定                  | CI の信頼性低下 | E2E は主要シナリオに絞り、ロジックは単体テストで担保                                     |
| 社内ポリシーで OSS 公開が制限される | 公開できない    | D6 を早期に確認、社内情報を含めない運用（DoD 6）                                         |
